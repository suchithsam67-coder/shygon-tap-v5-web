Production readiness audit

SHYGON Tap V5

End-to-end test of the customer web application — build, authentication, catalogue, checkout, Razorpay payment path, Netlify Functions, Supabase RLS, admin authorization, and responsive UI.

Date 12 Sep 2026 Artifact shygontapv5_complete.zip Suites run 4 Assertions 106
Final verdict
Not production ready

The application cannot reach its database. The Supabase project this repo documents as live — shygon-tap-v5 — stopped resolving between 17 and 26 September. It was most likely paused for inactivity, though only the Supabase dashboard can confirm. Everything downstream of that — signup, orders, payment fulfilment, entitlements, Tap provisioning — is blocked, not passing.

The code itself is in notably good shape. Security architecture, RLS and payment verification are genuinely strong and verified by test. One blocker remains — it is configuration, not a rewrite. Four defects were found and fixed, including a time bomb in the project’s own test suite.

This network rewrites DNS

Plain DNS here is intercepted by the ISP, even when sent to 8.8.8.8 or 1.1.1.1: names that do not exist come back as 49.205.75.11, which serves “No site configured”. Dead hosts look alive. Only DNS-over-HTTPS gave trustworthy answers, and it is what the statements above rest on.

To unblock: open shygon-tap-v5 in the Supabase dashboard and restore it if it shows Paused — if it is missing, that is a larger problem than configuration. Then copy its publishable key into .env; the URL and service-role key are already correct. If it was paused for inactivity, the production site would go down the same way the first quiet week after launch, so check the plan before launch.

A caveat worth knowing about your existing test suite

The project's db:verify runs as the PGlite superuser, which bypasses row-level security entirely. Its 21 passes prove your triggers and business rules — they do not prove RLS. P1

localhost was being baked into printed QR codes

Fixed
Feature
QR generation / NFC public URL / every absolute link
Problem
The supplied .env structure set VITE_SITE_URL=http://localhost:5173, and the string was confirmed compiled into dist/assets/AccountApp-*.js. Any QR generated from such a build encodes localhost — and a card already in someone's wallet cannot be reprinted.
Blast radius
Wider than the QR. CONTACT_EMAIL derives from the same value, so the live footer rendered contact@localhost:5173 — seen on the rendered page. Open Graph URLs, the shareable Tap link and the Razorpay checkout logo all inherited it too.
Root cause
Config, not code. src/lib/site.ts was already correct — it defaults to https://shygontech.com and deliberately does not read window.location.origin. So there was nothing to find in a code review; the problem was that a bad value could ship silently.
File
vite.config.ts, .env, .env.example
Fix
Two parts. The value was commented back out in .env (unset is the correct production state). More importantly vite build now refuses to produce a bundle whose VITE_SITE_URL is not a public https origin, and says why. Staging is unaffected — any https origin passes — and ALLOW_LOCAL_SITE_URL=1 is the deliberate escape hatch for a local preview. The dev server is untouched.
Verification
Six cases exercised: unset → builds; https://staging.shygontech.com → builds; http://localhost:5173 → refused; http://192.168.1.50:5173 → refused; http://shygontech.com → refused; escape hatch → builds. Then on a clean build: no localhost:5173 in dist/, exactly one canonical origin (https://shygontech.com), footer now reads contact@shygontech.com, og:url now https://shygontech.com/.
Status
Fixed. Downgraded from P0 to P1: it can no longer reach production silently.
P1

No Node version pinned — every payment function would 500 on Node 20

Fixed
Feature
All four Netlify Functions
Problem
@supabase/supabase-js v2.112 builds a RealtimeClient inside createClient, which needs a native WebSocket — absent before Node 22. I reproduced it: “Node.js detected but native WebSocket not found.” Every function calls adminClient(), so on a Node 20 runtime order creation, verification and webhook fulfilment all return 500 — payments dead, silently, in production.
Root cause
No .nvmrc, no .node-version, no NODE_VERSION in netlify.toml, no engines field. The runtime was left to Netlify's rolling default.
File
netlify.toml, package.json
Fix
Added [build.environment] NODE_VERSION = "22" and "engines": { "node": ">=22.12.0" }, with a comment explaining why so it isn't removed later.
Verification
Build re-run clean after the change. Note the local machine still has Node 20.18.0, which is why one function assertion remains blocked locally.
Status
Fixed.
P2

Four identical full-table catalogue fetches per page view

Fixed
Feature
Storefront pricing
Problem
Measured in the production build (not a StrictMode artifact): 4 identical /rest/v1/products requests for one view of /shygontap, each returning the entire products table with 18 columns.
Root cause
Four components price themselves independently — hero, configurator, store grid, product detail — and each ran its own fetchCatalog() on mount with no shared cache.
File
src/services/catalog.ts:79
Fix
In-flight de-duplication plus a 30-second result cache inside fetchCatalog, rather than lifting state — the callers are deliberately independent and any may render alone. A failed load is never cached, and invalidateCatalog() is exported.
Verification
Logic tested directly: 4 concurrent mounts → 1 query; later reads within TTL → 0 extra; concurrent failures share one attempt and recover cleanly afterwards. Build and lint re-run clean.
Status
Fixed. The full 4→1 reduction can only be observed end-to-end once a reachable database exists.

Before launch step 3 is now enforced by the build

  1. Restore shygon-tap-v5 and add its publishable key
    In the Supabase dashboard. The URL and service-role key in .env are already correct for it. Nothing else can be tested until this is done.
  2. Re-apply migrations 001–010
    The schema is largely present but has drifted in at least one function. The migrations are proven idempotent locally. Then run node supabase/tests/live-auth-rls.mjs . against it.
  3. Confirm VITE_SITE_URL is unset or the real domain in Netlify
    Now enforced: the build refuses a bundle whose canonical origin is not a public https URL, so this can no longer be got wrong silently. Just do not set the variable in Netlify.
  4. Run one real Razorpay test-mode payment end to end
    Order → checkout → verification → entitlement → Tap provisioning. This is the single largest untested path, and it is untested only because of the credential blocker.
  5. Register the webhook and replay an event twice
    Confirm the second delivery is answered “already processed” and grants nothing additional.
  6. Set the four server secrets in Netlify
    RAZORPAY_KEY_SECRET, RAZORPAY_WEBHOOK_SECRET, SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY — never with a VITE_ prefix.
