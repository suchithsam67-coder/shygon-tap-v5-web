## 2. Authorization: nothing found

- **The four recreated functions kept their shape.** `modes_owner_state`, `modes_owner_activate`, `modes_preview` and `get_public_tap_mode` are all `SECURITY DEFINER` with `SET search_path TO 'public', 'pg_temp'` (`036:225,279,348,378`) — the same pair 034 used. **`git grep -E '^(GRANT|REVOKE)'` on `036_lost_mode.sql` finds nothing**, so 034's grants stand unchanged: everything revoked from `PUBLIC`/`anon`/`authenticated`, `service_role` granted, and only `get_public_tap_mode` open to `anon` + `authenticated`. *OBSERVED:* `test:modes` — "9 server-only functions, 1 public reader"; `test:db` — admin-contract 17, with `get_public_tap_mode(text) (anon, authenticated)` the only modes entry in `APPROVED_CLIENT_EXECUTE` (`admin-contract.mjs:160-170`), so a new client-executable function fails that gate whatever its name.
- **No caller-supplied identity.** `modes.mjs:90,102,119` take the user only from `currentUser()` (the verified access token); no operation accepts a `userId`, `slug` or `role` from the body or the URL, so another owner cannot address another account. *OBSERVED:* the 401-before-any-op check and the cross-account checks (Cara only ever changes her own Tap while Asha's is on Lost) in Section C.
- **The catalogue row and the widened CHECK** (`036:218-220`) add no table, no policy and no grant. *OBSERVED:* `db:verify` 21, rls-matrix 1,565 (the mode tables stay 0 rows / 0 affected for all seven callers), admin-contract's "30 existing identical; new: … tap_mode_catalog, tap_mode_state, tap_mode_audit (closed, RLS on)".
- **The mode audit is still append-only** and holds field names only — unchanged by 036, still asserted by `test:modes` A.

## 4. State, switches and races

- **Idempotency and `expectedVersion` are the generic 034 machinery**, unchanged; a Lost activation replays even after the catalogue goes off (probe), which is exactly what makes finding #3's relay-side asymmetry visible.
- **Lock order (2026-10-25 review #4) still holds.** 036 takes no new lock; the static pin (`modes.mjs:75-95`) passes against this commit's `modes_owner_activate` body, and the Info writers are byte-identical to 034's.
- **Activate vs opt-out** — finding #5: fails closed, no deadlock.
- **Opt-out while Lost is active** is the state the reader's `rescue_public_target` gate exists for, and the suite exercises it directly (`modes.mjs:394-396`): reader `null`, owner sees `needs_setup ['returnToOwner']`.
- **Suspended Tap or account** blocks activation (`tap_suspended`, `036:303-306`) and the reader alike — asserted in Section C and in the Info-mode F-5 check.

## 5. Contract vs code

- **Everything §6 v0.10 publishes matches the code:** `lost` in `MODES` (`modes.mjs:45`); `mode_unavailable` (409) for a Lost activation with the relay off (`modes.mjs:100`, *OBSERVED* in the suite) **and** with the catalogue off and the relay on (`036:307-308`, *OBSERVED* in probe 2 — the database's own gate, not the JavaScript one); `needs_setup` + `missing: ['returnToOwner']` without the opt-in (`036:325-327`); `owner.state`'s documented precedence — relay off or catalogue off → `not_available`, catalogue on + relay on + opt-in off → `needs_setup ['returnToOwner']`, then `ready`/`active` (`modes.mjs:91-93` mapping over `036:263-272`, *OBSERVED* in the suite and both probes); the §6 key-set check passes over 25 success answers on 6 operations.
- **Three mismatches: findings #1 (preview vs visitor), #2 (§6 lines 179 and 180 conflict) and #3 (replay promise).** Nothing else disagreed in my reading; the draft customer copy in §6 lines 222-226 is a Session B gate, not a backend obligation.
